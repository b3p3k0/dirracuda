# OWASP ASVS assessment of the Dirracuda web UI (feature/secure‑webui)

## Overview

The Dirracuda web interface added in the `feature/secure‑webui` branch is a self‑hosted FastAPI application that exposes dashboards and scanning controls for Dirracuda.  The UI is not intended to be publicly available and remote access is disabled by default.  It uses a simple username/password login, server‑side sessions and CSRF tokens.  To evaluate it against the **OWASP Application Security Verification Standard (ASVS)**, the latest stable version (v5.0.0, May 2025) was consulted【78857878989853†L61-L69】, along with the annotated ASVS guide to understand individual requirements such as password hashing【212803036719298†L69-L71】, session token randomness【141819867666172†L55-L58】 and CSRF protection【804247887621786†L54-L57】.

The assessment below focuses on ASVS Level 2 (suitable for applications handling sensitive data) and maps the web UI’s behavior to ASVS requirements.  Each area is marked **Pass**, **Partial** or **Fail**.  A separate table lists remediation recommendations prioritized by severity.

## ASVS control summary

| ASVS area | Key requirements (Level 2 examples) | Observations for Dirracuda web UI | Pass/fail |
|---|---|---|---|
| **V1 Architecture, design & threat modelling** | Identify all components and dependencies; define high‑level architecture; separate data, control and display; assess threats and mitigate them【586443285481515†L6-L20】. | The web UI’s architecture is simple (FastAPI server plus Jinja2 templates).  Configuration (`webui.json`) declares bind address, port, allowed CIDRs, TLS options and session time‑outs.  However there is no documented threat model or architectural diagram. | **Partial** – the code shows segregation of concerns (route handlers separate from templates), but lack of formal threat modelling and documentation. |
| **V2 Authentication** | Use strong password hashing; no username enumeration; protect against brute force attacks; enforce secure transport; avoid default credentials【212803036719298†L69-L71】. | Credentials are stored in a JSON file and hashed using PBKDF2‑HMAC‑SHA256 with a 256‑bit salt and 600k iterations (strong hashing).  Login failures return a generic error and `verify_password` does not reveal whether a user exists.  There is no default user/password by default.  Transport security is enforced when remote access is enabled.  **Weaknesses:** there is no password complexity policy, no account lockout or throttling, and no multi‑factor support.  Remote login attempts can be brute‑forced. | **Partial** – strong password hashing and no enumeration pass, but missing rate‑limiting/brute‑force protection and password policy. |
| **V3 Session management** | Session IDs should be long, random and unique【141819867666172†L55-L58】; sessions should have idle and absolute time‑outs; tokens protected by `HttpOnly`, `Secure` and `SameSite`; sessions invalidated on logout; avoid exposing session IDs in URLs. | The `SessionStore` generates 256‑bit hex session IDs and CSRF tokens.  Sessions are stored server‑side and include idle and absolute timeouts from the config.  On login, the server sets an HTTP cookie with `HttpOnly` and `SameSite=Strict` flags; the `Secure` flag is set when TLS is enabled.  `app.py` invalidates sessions on logout and clears the cookie.  Session IDs are never placed in URLs.  However there is no ability for users to view/terminate other sessions and no concurrent session detection. | **Pass (with minor gaps)** – the core session management requirements are met; lacking multi‑session management is a low‑risk Level 2 gap. |
| **V4 Access control** | Enforce authorization at the server; prevent direct object reference issues; use least privilege; protect against CSRF【804247887621786†L54-L57】; enforce same‑origin. | All routes, except login and static assets, depend on `AuthRequired`.  The server checks `request.client.host` against allowed CIDRs and rejects unauthorized remote clients.  A CSRF token is generated per session and validated on every state‑changing request.  A same‑origin check rejects requests with mismatched `Origin` or `Referer`.  The UI has only one user role (administrator), simplifying authorization; there is no direct object reference exposure. | **Pass**. |
| **V5 Input validation & malicious input handling** | Validate all inputs on the server side; enforce length/format; prevent injection attacks (SQL, OS, command); ensure input fields are strongly typed【586443285481515†L74-L88】. | JSON APIs use Pydantic models for input, enforcing types and length limits (e.g., `ScanRequest` validates protocol, country codes, `max_shodan_results`, filter string length and absence of control characters).  SQL queries in `db.py` are parameterized; search strings and pagination values are sanitized.  CLI commands are built from validated `ScanRequest` and not directly influenced by user input.  **Weakness:** some SQL statements are built via string interpolation (e.g., assembling “union all” queries) – currently safe because the interpolated parts are static, but any future user‑defined SQL fragments would be dangerous. | **Pass (with caution)**.  Input validation is thorough, but dynamic SQL construction should be reviewed periodically. |
| **V6 Output encoding / escaping** | Use context‑appropriate output encoding; escape user‑controlled data; use frameworks with auto‑escaping. | The UI uses Jinja2 templates, which perform HTML auto‑escaping by default.  Application data displayed in templates (e.g., host names, task IDs) comes from the database or sanitized Pydantic models; there is no evidence of unescaped injection into JavaScript contexts. | **Pass**. |
| **V7 Cryptography at rest** | Use strong random numbers for secrets; protect secrets at rest; manage cryptographic keys securely【586443285481515†L94-L103】. | Sessions and CSRF tokens are generated using Python’s `secrets` module (cryptographically secure).  Passwords are hashed and salted.  However, the credential file (`webui_creds.json`) is only hashed; there is no encryption of configuration or database exports.  Because the application is meant for local administration, encryption of the database is not critical, but storing credentials in a JSON file is riskier than using a password manager or OS keystore. | **Partial** – strong random tokens are used, but secrets are not encrypted at rest. |
| **V8 Error handling & logging** | Do not leak sensitive information in error messages; log security‑relevant events; ensure logs are complete【586443285481515†L115-L120】. | The server returns generic error messages for login failures and configuration errors; exceptions are translated into plain error strings without stack traces.  Login successes and failures are logged.  There is no evidence of secrets being logged. | **Pass**. |
| **V9 Data protection & privacy** | Do not send sensitive data in URLs; clear sensitive data from client cache; minimize storage of PII【586443285481515†L121-L125】. | Session IDs are stored only in cookies and never appear in URLs.  There is no user‑provided PII other than credentials.  The application does not write sensitive data to logs or client storage. | **Pass**. |
| **V10 Communications security** | Use TLS for all authenticated interactions; protect data in transit; use strong cipher suites【586443285481515†L115-L120】. | Remote access is disabled by default; when enabled, the configuration enforces TLS by requiring a certificate and key.  If TLS is disabled for remote access, `allow_insecure_remote` must be explicitly set in the config; otherwise the configuration is rejected.  Cookies are marked `Secure` when TLS is enabled.  There is no support for HSTS, and the server does not set HTTP Strict‑Transport‑Security or other security headers. | **Pass (with recommendations)** – core TLS enforcement is present; adding HSTS would strengthen it. |
| **V11 HTTP security configuration** | Configure secure headers (CSP, HSTS, X‑Content‑Type‑Options, X‑Frame‑Options); ensure cookies use appropriate flags; avoid unnecessary HTTP methods. | Cookies are set with `HttpOnly`, `SameSite=Strict` and `Secure` (when TLS).  The application returns JSON responses or HTML pages and does not reveal server internals.  However, the web UI does not set security headers like `Content‑Security‑Policy`, `X‑Frame‑Options`, `X‑Content‑Type‑Options` or `Referrer‑Policy`. | **Partial** – cookies are secure, but missing standard security headers. |
| **V12 Security configuration** | Centralize and validate security configuration; ensure configuration files are protected; use sensible defaults【586443285481515†L6-L20】. | `webui.json` holds configuration; `config.py` validates types, ranges and ensures remote connections require TLS or an explicit insecure override.  The file is written atomically with permissions 600.  Default configuration disables remote access and sets conservative timeouts. | **Pass**. |
| **V13–V19 (malicious controls, internal security, business logic, files/resources, mobile, web services, configuration)** | Level 2 focuses on verifying that internal operations do not introduce injection or tampering risks, that business logic prevents abuse, and that file uploads and web services are protected. | The UI delegates scans to CLI scripts via controlled `ScanQueue`, validates all parameters and uses fixed protocol commands.  There are no file uploads, external web services or mobile components.  Therefore these areas are not applicable or are covered by earlier controls. | **N/A / Pass**. |

## Findings and remediation plan

| Issue | Severity | Evidence / rationale | Recommendation |
|---|---|---|---|
| **No rate‑limiting on login** | **High** | ASVS requires protection against brute‑force attacks and user enumeration【212803036719298†L69-L71】.  The current login API allows unlimited password guesses. | Implement login rate‑limiting (e.g., exponential backoff, CAPTCHA or temporary account lockout after consecutive failures).  Consider logging IP addresses to detect abuse. |
| **Missing password policy and multi‑factor authentication** | **Medium** | The application accepts any password and does not enforce length or complexity, and there is no option for multi‑factor authentication. | Enforce a password policy (minimum length, complexity or passphrase).  Provide optional multi‑factor authentication (e.g., TOTP) for administrators. |
| **No account management (password reset, account lock, deletion)** | **Medium** | Users cannot change their password or reset credentials; if the credential file is lost or compromised, recovery is manual. | Add endpoints to change credentials securely (with current password verification and CSRF protection).  Provide a CLI tool to reset credentials. |
| **Lack of standard security headers** | **Medium** | HTTP responses do not include `Content‑Security‑Policy`, `Strict‑Transport‑Security`, `X‑Content‑Type‑Options`, `X‑Frame‑Options` or `Referrer‑Policy`.  ASVS emphasises secure configuration【586443285481515†L115-L120】. | Configure FastAPI middleware to set these headers.  For example, add a `Content‑Security‑Policy` limiting resources to `self`, enable `HSTS` when TLS is used, set `X‑Frame‑Options: SAMEORIGIN`, `X‑Content‑Type‑Options: nosniff` and `Referrer‑Policy: same-origin`. |
| **Credential storage in JSON file** | **Medium** | Credentials are stored in a local JSON file (`~/.dirracuda/conf/webui_creds.json`).  Even though passwords are hashed and salted, the file itself is not encrypted and might be accessible if file permissions are misconfigured. | Use a system key store (e.g., OS keychain) or encrypt the credential store using a master key.  At minimum, confirm file permissions (0600) and document operational procedures to protect the file. |
| **No documented architecture or threat model** | **Low** | ASVS encourages documenting architecture, data flows and threats【586443285481515†L6-L20】.  The repository contains no design or threat modelling documentation. | Produce a simple architecture diagram, data flow and trust boundaries.  Document threat assumptions and mitigations for the web UI, including remote access scenarios. |
| **Dynamic SQL construction** | **Low** | In `db.py`, some SQL strings are concatenated to build union queries.  Today all variables are static, but this pattern can lead to injection if user‑controlled data is inserted. | Use parameterized queries and avoid string concatenation for SQL.  Where dynamic building is necessary, ensure interpolated parts are constants or validated against an allowlist. |
| **No concurrent session management** | **Low** | Users cannot view or revoke other active sessions.  ASVS suggests users be able to manage sessions. | Provide a mechanism to list active sessions and terminate them. |
| **Missing Content Security Policy in templates** | **Low** | Without `Content‑Security‑Policy`, browsers may execute injected scripts. | Set a restrictive CSP header.  Ensure inline scripts use nonces or separate JavaScript files to conform to CSP rules. |
| **In‑memory session store** | **Low** | Sessions are stored in memory and lost on server restart (not a security issue but affects usability). | Optionally persist sessions to a secure backend (e.g., Redis) and provide session revocation across restarts. |

## Summary

The Dirracuda web UI demonstrates a thoughtful approach to security: strong password hashing and random session tokens, CSRF protection, strict origin and CIDR checks, secure cookie flags and robust input validation.  These measures satisfy many of the ASVS Level 2 requirements.  The remaining gaps mainly involve hardening of authentication (rate‑limiting, password policy, multi‑factor), addition of standard security headers, protection of the credential store and documenting the architecture and threat model.  Addressing the high‑ and medium‑severity findings above will substantially improve the security posture of the web UI and align it more closely with the OWASP ASVS.
